## Verified ground truth (established before the panel)

These are facts, not opinions. Citations are to commands run on 2026-05-24.

1. **The documented verifier command crashes on this machine.** Spec §11 and the handoff both say to run `python3 scripts/verify_article_epistemic_layer_contract.py --strict`. 2. **The published payload is not self-verifying.** Each layer in `data/ka_payloads/article_epistemic_layer.json` emits `"release_eligible": false` (a JSON boolean; `build_…_layer.py:1197` calls `bool(...)`). The hash matches only if you coerce `false` back to `int 0` — knowledge that lives in the DB-bound verifier, not in the artefact. Spec §13's "every public payload hash matches the lifecycle database record" is technically satisfied; the artefact's hash is nonetheless **uncheckable by any consumer who only has the file.**

3. **Zero of 760 records are `fresh`.** Real-DB distribution: `freshness_status` = 758 `stale`, 2 `unknown`, **0 `fresh`**. `render_status` = 2 `renderable`, 758 `show_with_warning`. The 2 "renderable" papers (`PDF-0014`, `PDF-0045`) are renderable **because their PNU row is missing** (`freshness=unknown`), not because anything passed — they render on an *absence* of belief-network data. `extraction_status` = `complete` for all 760. `release_eligible` = 0 for all 760. `review_status` = `unreviewed` for **all 760** — the vocab value `machine_verified` is never written by anything in Stage 1.

4. **All 758 open completion-queue items are `pnu_requires_repair` / `blocking`.** Single reason, single severity.

5. **Two builders, one database, no integration — and it is live, not hypothetical.** The same `160sp/pipeline_lifecycle_full.db` contains the implementer's `article_epistemic_*` tables (760 records populated) *and* the overseer's `artefact_registry` (3 rows), `claims` (**0 rows**), `defeaters`, `belief_network_links`, `answer_shape_decisions`. `from overseer import article_epistemic_builder` imports cleanly — its dependencies resolve. ## Situation summary (plain prose, before the panel)

### 1. What the module does today

Run `build_article_epistemic_layer.py` and, for each of the 760 papers in `article_details.json`, it derives one "epistemic record" with seven components — `primary_claim`, `claim_rows`, `evidence_strength`, `defeaters`, `belief_network_context`, `answer_shape_status`, `provenance_summary` — by deterministic rules over fields the upstream pipeline already extracted (`top_claims`, `argumentation`, `evidence_profile`, `pnu`, `article_meta`, `science_summary`). It never calls an LLM. It writes six lifecycle tables (records, components, support_sets, build_runs, completion_queue, verification_events), assigns stable IDs (`record_id`, `component_id`, `claim_id`, `support_set_id`), hashes everything with canonical JSON + SHA-256, and emits a 9.4 MB sibling JSON payload. When a required input is missing or stale it writes a typed `absence_reason` and an upsert-deduped completion-queue row rather than fabricating content.

Run the verifier and it proves a **closed, internal consistency property**: that the rows in the DB hash to what they say they hash to, that vocabularies are respected, that referential links resolve, that no component is flagged `llm_generated`, and that one active record exists per paper. It does **not** prove that the content is correct, that the claim selected is the paper's actual main claim, that the evidence strength means anything, or that the page will render. It writes its own results to `verification_events` but **never updates the record it verified** — which is why `machine_verified` is unreachable.

The sibling payload gives a downstream renderer, per paper: six split status fields, a primary claim id, four counts, and seven component objects each carrying status / source_mode / field_policy / review_status / freshness / render_policy / display_label / content / absence_reason / support_set hash / provenance / verification. It is shaped to be rendered directly.

### 2. Where it is going

- **Phase 3 — page render.** `ka_article_view.html` shows the layer with visible provenance, empty/stale states, mobile-safe layout. **Blocked on:** the render-contract verifier `verify_article_epistemic_render_contract.py`, which **does not exist** (confirmed). Also blocked, practically, by the fact that 758/760 records render only `show_with_warning`.
- **Phase 4 — release gate.** Twelve conditions (spec §13), fail-closed. **Blocked on:** Phase 3, and on the fact that `release_eligible` is hard-wired to 0 (`build:880-882`) with nothing that can flip it.
- **Phase 5 — Stage 2 LLM enrichment.** Field-policy-gated, subscription-CLI-only, source-packet manifests, grounding verifier, review gates. **Blocked on:** all of the above plus a write-path decision (see §two-builders).
- **AEPL-PNU-REPAIR-BACKLOG.** The 758 `pnu_requires_repair` items. **Blocked on:** the upstream PNU pipeline, which is not part of this module.

### 3. Strengths, in three sentences

The split-status vocabulary and typed-absence discipline genuinely prevent the "what does `complete` mean" failure that the prior panel rejected, and the builder honestly refuses to manufacture content it does not have. The hashing and support-set machinery is internally coherent and recomputes exactly (the verifier's content/support/payload-hash checks pass on all 760, which is not nothing). The module does the rare honest thing of surfacing that 758/760 papers are upstream-broken instead of papering over it.

### 4. Promises implicitly made by shipping this

A renderer, a downstream agent, or the next engineer will now assume — *because Stage 1 exists and emits this shape* — that:

- the seven component keys are stable and present on every record (true today, load-bearing forever the moment a page reads them);
- `payload_hash` lets a consumer verify the artefact it holds (**false** — finding #2);
- `freshness_status: fresh` is a state the system actually reaches (**false today** — 0/760);
- `review_status: machine_verified` is reachable (**false** — never written);
- `release_eligible` is a field that will eventually become `true` for good records (true intent, but flipping it changes `payload_hash` and invalidates every stored hash — finding below);
- `primary_claim` is *the* claim of the paper (it is the top-ranked `top_claims` row, which is a different and weaker promise);
- `defeaters` models defeat (it is a count of argumentation edges with an empty `rows: []` and no target field);
- the `support_set` identifies the *source*, durably (it identifies the source **at a file path** — `build:191` hard-codes `data/ka_payloads/article_details.json`).

### 5. Weaknesses nameable before any panelist speaks

The happy path is the empty set (0 fresh records). The verifier proves form, not warrant. The documented command crashes. The artefact's own hash can't be checked from the artefact. There are two builders for one artefact in one DB. `defeaters` has no target field. And the single production build run means the entire versioning story is untested.

## Round 1 — Read the Room (≤150 words each)

**Pollock.** A page called "defeaters" that contains `rows: []` and an integer is not a defeater model; it is a placeholder wearing the word. I'll grant the honesty: `no_defeater_extracted` is at least distinguished from a populated set. But the strength I cannot accept is the implicit claim that `attack_count` *is* defeat. Defeat is a relation between a defeater and a specific inference — rebutting the conclusion or undercutting the link. The schema has no slot for which inference is defeated or how. The weakness visible from the spec alone: §8 demands target-specific defeaters (claim/warrant/method/…) and the shipped builder produces none, while the *other* builder in this repo produces exactly those. **Mayo.** My question is the only one that matters for a thing called "evidence strength": severity. A claim is warranted by evidence to the degree it has *passed a test that would have caught it had it been false.* `evidence_strength` here copies a per-claim `credence` and staples on `support_count`/`attack_count`. None of those quantities is the output of a test with an error probability. I'll acknowledge one real virtue: `confidence_basis` is recorded, so at least the provenance of the number is auditable. **Haack.** Show me where mutual support lives. ## Round 2 — Shred the Implementation

### Helland — the two builders, the swap, and identity-on-a-path

Two builders write the same artefact through incompatible paths. `scripts/build_article_epistemic_layer.py` writes `article_epistemic_records/_components/_support_sets` directly. `overseer/article_epistemic_builder.py` (`build_one`, lines 238-491) writes `claims`, `defeaters`, `belief_network_links`, `answer_shape_decisions`, `content_hashes`, and gates the final mutation through `update_with_hashes(..., fencing_token=…)` (lines 467-476), which raises `FencingTokenMismatch` on a stale token. I verified both table families live in the same `160sp/pipeline_lifecycle_full.db`: the implementer's records number 760; `claims` is empty. So right now one artefact ("the epistemic record of PDF-0007") has a populated representation in one table family and an empty stub in another, **in the same file**, with no foreign key, no shared id space (`record_id` strings happen to collide by format — `article_epistemic_layer.v1:{paper_id}` — but nothing enforces agreement), and **divergent logic**: the two `select_primary_claim`s read different fields (implementer reads `finding`, `build:283`; overseer reads `canonical_claim_text`/`text`, `overseer:146-147`), and the two `answer_shape` assigners use entirely different rule sets (`build:762-773` vs `overseer:156-207`). The instant someone runs the overseer builder, the same paper can get a *different primary claim and a different answer shape* depending on which table you read. The implementer's builder has **no fencing token and bypasses `artefact_registry` entirely**, so it cannot even participate in the overseer's concurrency control.

The swap itself: `persist_record` (`build:1104-1132`) does `UPDATE … SET active=0 WHERE active=1` then `INSERT … active=1`. The partial unique index `uq_aer_active_per_paper_schema` (`schema:106-108`) will *catch* a violation by erroring, but it will not *prevent* a lost update: two concurrent transactions can both deactivate, one inserts, the other's insert either collides (abort, lost build) or, with different `build_run_id`, both could attempt active=1 and the index aborts the second — meaning a concurrent rebuild **fails noisily and is dropped** rather than serialized. There is no `BEGIN IMMEDIATE` and no row lock; the enclosing `with conn:` is SQLite's deferred transaction. **Minimum fix:** pick one write path. Either the implementer's builder is rewritten to register artefacts and call `update_with_hashes` with a fencing token (route through the overseer), or the overseer's epistemic builder is deleted from the tree until Stage 2. Two builders for one artefact is not a tech-debt item; it is a correctness bomb with a lit fuse.

### Brooker — the runbook crashes, the corpus is empty of fresh records, the happy path is the null set

I'll take the three operational facts in order. **(a)** The documented command crashes. `verify_…_contract.py:143-152` returns the first existing DB; the first existing DB is a 0-byte decoy; line 738's `exists()` guard waves it through; line 561 throws `no such table`. There is no try/except around the per-record queries (`verify_all`, lines 600-634), so the operator gets a Python traceback, not "DB looks empty." **(b)** Zero fresh records. I queried it: `freshness_status` is 758 `stale`, 2 `unknown`, 0 `fresh`. The *only* two `renderable` records (`PDF-0014`, `PDF-0045`) got there by having **no PNU at all** (`unknown` beats `stale` in `derive_record_statuses`, `build:857-871`). So the system's two best-looking pages are its two most-ignorant pages. **(c)** The happy path doesn't exist in production. The fixture `complete_record` (`_article_epistemic_fixtures.py:73-128`) has `requires_repair=False`, `status="verified"` PNU. **No production record matches that shape** — 0/760. The 42 tests (which pass in 0.13 s) are exercising a configuration the corpus never produces. **Minimum fix for (a):** when `resolve_db_path` returns a file, assert the schema tables exist before querying, and exit 2 with "DB present but un-initialized at {path}; did you mean --db 160sp/…?" Better: refuse to auto-pick a 0-byte file. **Minimum fix for (c):** add a fixture `production_typical_record` with `requires_repair=True` and assert the *stale* path's full output, because that is 99.7% of reality. The `make_build_run_id` microsecond fallback (`build:162-165`, `next_seq = datetime.now().microsecond or 1`) is a real but minor collision risk confined to dry-run/`conn=None` paths; I rank it far below (a)–(c).

### Wright — the payload is a public API and it disagrees with itself

The sibling JSON is a contract the moment it exists; Hyrum's Law says every field in it is now load-bearing. Two observations, both file-cited. **First, the self-contradiction.** `build_public_payload` emits `"release_eligible": bool(rec["release_eligible"])` → `false` (`build:1197`). But `payload_hash` was computed by `build_record_for_paper` over `**statuses`, where `release_eligible` is the integer `0` (`build:880-882, 988-996`); the verifier recomputes from `record["release_eligible"]`, also the DB integer (`verify:384`). I recomputed `PDF-0001`'s hash from the *published JSON's* `false` and got `683ac5…` vs stored `fcd1a4…` — **mismatch**. So a downstream consumer that does the obvious thing (hash the object you received, compare to the `payload_hash` it carries) fails, and by Hyrum's Law someone will write exactly that consumer. **Second, the evolution trap.** `payload_hash` covers `release_eligible` (`verify:375-389`). It is pinned to 0 across all 760 records. The entire *point* of Stage 4 is to flip some records to eligible. The day that happens, `payload_hash` changes for every promoted record, invalidating any downstream system that keyed on or cached the old hash — including the spec §13 check "production serves the same artifact hash as the release artifact." **Minimum fix:** (i) compute and store `payload_hash` over a canonical form that matches the published bytes exactly — either hash `true/false` and emit `true/false`, or hash `0/1` and emit `0/1`, but the artefact and its hash must agree; (ii) decide whether `release_eligible` belongs *inside* the hashed payload at all — I'd pull it out into an unhashed envelope field so promotion doesn't rewrite content hashes. **Minimum test:** load the published payload, recompute every `payload_hash` from the file alone, assert equality. That test does not exist and it would fail today.

### Pollock — the defeater component implements counting, not defeat

`build_defeaters_component` (`build:569-676`) sets `mapped_rows = []` unconditionally (line 585, with the comment "Stage 1 does not synthesize defeater rows") and then branches on `argumentation.attack_edge_count` and `contradicting_papers` to choose an `absence_reason`. There is no field anywhere in the emitted content for **what is defeated** or **how**. Compare the spec: §8 requires defeaters be "target-specific: claim, warrant, method, measurement, interpretation, generalizability, mechanism, or application." That enumeration is precisely the set of inferential joints an undercutting defeater can attack. The shipped builder produces none of them. Meanwhile `overseer/article_epistemic_builder.py:_classify_defeaters` (lines 210-231) **does** enforce `target_kind ∈ {claim, warrant, method, measurement, interpretation, generalizability, mechanism, application}` and *rejects* any defeater lacking it. So the repository contains a correct implementation of my distinction — in the builder you did not ship. Two further confusions. First, the layer never distinguishes a **rebutting** defeater (reason to believe ¬claim) from an **undercutting** one (reason the warrant doesn't transmit support) — both collapse into "attack." For a system whose entire selling point is epistemic honesty, erasing that distinction is the cardinal sin; an undercut leaves you with *no* justified belief either way, a rebuttal gives you a reason for the opposite, and a reader must know which. Second, `no_defeater_extracted` is correctly held apart from a populated set, but the deeper pair I care about — `no_defeater_extracted` (we didn't look hard enough) vs. `no_defeater_exists` (we looked and there are none) — appears in the spec (§8) and **not** in the code; the builder only ever emits the former. **Minimum fix:** add `target_kind` and `defeat_kind ∈ {rebutting, undercutting}` to the defeater row shape now, even while `rows` stays empty, so the schema can hold a defeat relation when extraction arrives; and adopt the overseer's controlled vocabulary verbatim so the two builders can't disagree about what a defeater is. **Minimum test:** a fixture with one rebutting and one undercutting defeater on named targets, asserting both survive the round-trip with their `defeat_kind` intact.

### Gil — provenance that cannot replay, and identity bound to a path

PROV needs Entity, Activity, Agent. I can find Entities (the source fields, `build:188-196`) and weak Agents (`builder_version` strings buried in component provenance), but the Activity binding is broken where it matters. **`input_fingerprint` omits the builder.** `build:982-984`: it is `sha256(sorted(support_set_hash for each support set))` — inputs only. Bump `BUILDER_VERSION` from `v1` to `v2`, change the rules, rebuild with identical inputs, and you get an **identical `input_fingerprint`** — a silent regression where the fingerprint asserts "same provenance" across two different generating activities. Spec §6 says the fingerprint covers "all support set hashes for a record," so the *code matches the spec* — which means the **spec is wrong**, not just the code. **Identity on a path.** `_member` hard-codes `source_path_or_table="data/ka_payloads/article_details.json"` and builds `source_artifact_id="article_details_json:{paper_id}:{field}"` (`build:172-191`). Both strings are inside the hashed member dict, so renaming, moving, or sharding that file changes `support_set_hash` for all 5,320 support sets even though **not one source value changed.** That is the opposite of provenance: identity should survive relocation of the bytes. **No replay.** Nothing records the build command, the input snapshot beyond a single file hash, or a `wasGeneratedBy` edge from record → build run that a tool could follow to re-execute. **Minimum fix:** fold `schema_version` + `builder_version` into `input_fingerprint` (one-line change at `build:982`, plus the matching spec §6 redline); replace the path-coupled `source_artifact_id` with a content-addressed or registry-assigned identifier (the overseer's `artefact_registry` already mints these — another argument for one write path); add a `wasGeneratedBy` pointer from each record to its `build_run_id` in the public payload. **Minimum test:** rename the input file, rebuild, assert `support_set_hash` is unchanged when values are unchanged.

### Haack — the categories don't yet earn their keep

Two category-hygiene defects, both checkable. **First, `unreviewed` vs `not_required` is applied inconsistently to deterministic components.** `evidence_strength` (present) gets `review_status="unreviewed"` (`build:563`) but `answer_shape_status` — equally deterministic — gets `not_required` (`build:789`), and `evidence_strength` in its `not_applicable` branch also flips to `not_required` (`build:533`). All three are `source_mode="deterministic_derived"`. If determinism is the criterion for "not required," apply it uniformly; if reviewability is, then a deterministic component is never "unreviewed" in a meaningful sense. As written, the same property yields two different review states, which means the distinction is decorative. **Second, on my own crossword model there is no representation of mutual support at all** — claims do not secure one another, evidence has no independent-security score, and "comprehensiveness" (does this claim account for the relevant evidence?) is nowhere. `evidence_strength` is a per-claim credence plus edge counts; that is one cell of the crossword with no crossings. I will also defend the implementer on one pre-loaded point: the **primary-claim tiebreaker is *not* undetermined.** `select_primary_claim`'s sort key includes the enumerate index `idx` (`build:285-298`), which is unique, so the choice is fully deterministic. The real problem is subtler and worse: the de facto tiebreaker is *upstream list order*, which is itself unwarranted — two equally-supported claims resolve by an accident of extraction order, and the system presents the winner as "the primary claim" with no marker that the choice was arbitrary. **Minimum fix:** make `review_status` a pure function of `(source_mode, field_policy)` in one helper and call it everywhere; when the top-2 claims tie on `(support, attack, credence)`, emit `selection_was_arbitrary: true` so the renderer can hedge. **Minimum test:** two claims identical on all ranked keys → assert the `selection_was_arbitrary` flag, not just a stable winner.

### Smith — taxonomies that mutate are conceptualist, not realist

I gave the headline in Round 1; here is the file-cited body. **The `answer_shape` vocabulary changed between documents.** Brief (`…PANEL_BRIEF…:152`): `{toulmin, field_map, procedure, contrast_pair, ranked_brief, mixed}`. Spec §8 and the shipped builder (`build:762-773`): `{toulmin, field_map, comparison, mechanism, review_synthesis, mixed, unknown}`. Three of the brief's types (`procedure`, `contrast_pair`, `ranked_brief`) vanished; three new ones appeared. A realist taxonomy of "answer shapes" would not lose half its members in one revision — the churn shows these are coinages, not kinds. **The rules that assign them are nominalist in the worst way:** `field_map` fires when `signal` *starts with the string* `"direct measured"` (`build:768`) and `mechanism` fires when `warrant` starts with `"mechanism"` (`build:764`). You are classifying the world by the spelling of an upstream label; rename the upstream signal and the ontology silently reclassifies. **`review_status: machine_verified` is a dead category** — I checked, all 760 records are `unreviewed`, and nothing in the verifier writes `machine_verified` (it appends to `verification_events` and never `UPDATE`s the record). A vocabulary term that the system cannot reach is an ontological lie: it asserts a state of being that does not exist in this universe. **Minimum fix:** freeze the `answer_shape` vocabulary in the spec with a definition per term grounded in an observable structural property (not a label prefix), and *delete `machine_verified` from the vocab until the verifier actually writes it* — or make the verifier write it (see Mayo/Haack). **Minimum test:** assert every vocabulary value is reachable by some fixture; `machine_verified` fails that test today, which is the point.

### Mayo — the test that "passes" tells you almost nothing, because the path it exercises is not the path production runs

This is a severity argument about the *test suite*, not just the metric. The count-reconciliation logic is the one place the layer checks an epistemic relation (do defeater rows reconcile with attack counts?). The verifier's check reads `evidence_strength.attack_count` (`verify:418-451`), which the builder copies from the **primary claim's per-claim** `attack_count` (`build:549`). But the builder's *defeaters* component computes its counts from `argumentation.attack_edge_count` (`build:582`) — a **different field with different provenance.** The fixture `record_with_attack_count_no_defeaters` (`_fixtures:139-150`) has to set *both* `argumentation.attack_edge_count=4` *and* `top_claims[0].attack_count=4` to make the path light up. In production I checked the consequence: `argumentation.attack_edge_count` is ~0 for essentially every paper, so the reconciliation branch the test exercises **almost never fires in the corpus.** A test severely tests a claim only if it would probably fail were the claim false. This test cannot fail in the direction that matters, because the production distribution never enters the regime under test. So "42/42 green" is evidence of internal consistency and almost no evidence about behavior on the 760 real records. Add the freshness numbers — 0 fresh, 758 stale — and the picture is stark: the suite validates the configuration that occurs zero times and is silent on the configuration that occurs 758 times. **Minimum fix:** drive the test corpus from a sample of *real* records (or a faithful synthetic stale-PNU record) and assert the stale path's full record-level output, including `render_status=show_with_warning` and the blocking queue entry. **Minimum test:** a property test — for a random real record, the builder's `evidence_strength.attack_count` and `defeaters.attack_count_argumentation` either agree or the divergence is explicitly recorded as a count-basis; today they can silently disagree.

## Round 3 — Shred the Plan (Stages 2–5 + PNU-REPAIR-BACKLOG)

### Bender — Stage 2 is where the layer can launder form as meaning

The plan (spec §9, §5) says LLMs may populate `llm_enrichable` fields — "plain-language warrant explanation," "rebuttal synthesis," "competing-account summary" — gated by a field whitelist, source-packet manifests, output hashes, a "grounding result," and review status. Every one of those controls operates on *artifacts of the generation*, not on the relation between the generated text and the paper's actual content. Here is the structural problem, in my terms. An LM produces a distribution over forms conditioned on your prompt. It has no access to the paper's communicative intent; it has the source packet's *tokens*. So a "warrant explanation" is a fluent paraphrase of whatever you fed it, optimized to read like a warrant — the octopus answering about a bear it has never encountered. The plan's "grounding verifier" is named the way an architect says "scalable": it gestures at a guarantee without specifying the algorithm. Citation matching? Then it checks that strings co-occur, not that the explanation is *entailed* by the source. Entailment via NLI? Then you've replaced one fallible model's hallucination with another's. Retrieval consistency? That checks the explanation is consistent with retrieved text, not that it's *true of the paper*. None of these convert form into meaning; at best they bound how far the form drifts from the input form. And the **source-packet hash is the deepest confusion**: you can hash the manifest you *sent*, but the provider returns text generated from an opaque context window — the hash proves what you *intended* the model to see, never what it *used*. Concrete fix, and I mean this as the gate, not a nicety: **Stage 2 ships only behind a human-review queue for every public LLM field, with the generated text rendered under a persistent visual treatment that does not borrow the deterministic layer's authority** (different container, explicit "machine-drafted, unverified" until a human approves), and the "grounding verifier" is renamed to what it actually is — a **drift bound** — with its algorithm written down (I'd require span-level attribution: every clause in the explanation must cite a source span, and unattributed clauses are stripped before display). If you cannot attribute a clause to a span, you do not show the clause. That is implementable; "grounding" is not.

### Pollock — a generated "warrant explanation" cannot be defeater-aware, so it must not be shown as a warrant

Forward-looking: the plan wants LLM "plain-language warrant explanation." A warrant, in any usable sense, comes with its defeasibility conditions — the circumstances under which it *fails* to transmit support. A generated paraphrase that states the warrant without enumerating its undercutting conditions presents a defeasible inference as if it were conclusive. That is exactly the error my whole program exists to prevent. The fix is structural and cheap to state: **a warrant explanation field must be paired with a `defeasibility_conditions` field, and the renderer must refuse to display the former without the latter.** If Stage 1 cannot extract the defeaters (it can't, today), then Stage 2 cannot honestly explain the warrant, because the explanation would assert support the system cannot certify is undefeated. Concrete amendment: gate `llm_enrichable` warrant explanation on the presence of a populated, target-typed defeater set for the same claim — no defeater model, no warrant prose. This also forces the defeater schema fix from Round 2 to land *before* Stage 2, which is the correct ordering.

### Helland — the field-policy write path is undefined precisely because there are two write paths

Spec §9 says LLM writes are constrained "at the write path": field whitelist, no LLM-authored hashes/provenance/review status. My question is operational: *whose* write path? The Stage 1 builder does not go through `artefact_registry` and has no fencing token (Round 2). The overseer's builder does. If Stage 2 enforcement lives in `update_with_hashes` (the fenced path), then the implementer's builder cannot enforce anything — it doesn't call it. So you have two doors into the same room and a lock on only one. You cannot bolt field-policy enforcement onto Stage 2 without first collapsing to a single write path. Concrete fix, stated as a sequencing constraint: **AEPL-PHASE-5 must be blocked on a "single write path" task that either (a) rewrites `build_article_epistemic_layer.py` to register artefacts and mutate through `update_with_hashes`, or (b) deletes `overseer/article_epistemic_builder.py` and re-homes its `target_kind`/fencing logic into the shipped builder.** Until that lands, every Stage 2 governance promise is enforceable on at most half the writers. I have a mild preference for (a) because the overseer already implements the immutability/fencing model I'd want for "data on the outside"; but either is fine as long as *exactly one* survives.

### Wright — the release gate's twelve conditions need a defined failure mode, and the contract needs a deprecation policy

AEPL-PHASE-4 lists twelve release conditions (spec §13) but does not say what the gate *does* when one fails: fail-closed (block promotion), fail-open (promote with warning), or page a human. For a gate, undefined failure mode is the whole risk. And Hyrum's Law makes the payload contract a forever-commitment: the moment Phase 3 renders these fields, the field names, the enum values, and the *shapes* are depended upon. There is no `schema_version` negotiation in the payload beyond a string, and no policy for retiring a field. Concrete fixes: **(1)** specify the gate as fail-closed with an explicit, logged `gate_decision` artefact (which condition failed, which `build_run_id`, which records were withheld), and a single documented override path with reviewer identity + expiry (the spec already gestures at waivers in §12 — make the gate consume them). **(2)** Add a `payload_contract_version` distinct from `schema_version`, and a written deprecation policy: a field may be added freely, may be deprecated only with one release of overlap, and may be removed only after the overlap. **(3)** Resolve the `release_eligible`-in-hash problem from Round 2 *before* Phase 4, or Phase 4's first successful promotion will mass-invalidate hashes. Minimum test for the gate: a fixture corpus with one stale required component must yield `promote=false` and a `gate_decision` row naming the failed condition.

### Brooker — what does AEPL-PNU-REPAIR-BACKLOG look like at 3 a.m., and is "shipped" honest?

The honest framing: Stage 1 did what it was told, and what it was told surfaced that the upstream PNU pipeline has left 758/760 papers in `requires_repair`. That is a genuinely useful finding. But "Stage 1 complete" and "the artefact is renderable" are different claims, and the commit message blurs them — "760/760 records built … verifier 760/760 clean" is true and also compatible with "the page is unshippable for 99.7% of the corpus." Operationally, the backlog is the whole program: until PNU repair runs, Phase 3 renders 758 warning banners and 2 ignorance-by-omission pages. Concrete fixes: **(1)** Split the success metric in TASKS.md into *built* (760/760, done) and *releasable* (currently 2/760, and even those only by missing data) so no one reads "complete" as "usable." **(2)** Make the repair backlog a first-class pipeline with its own throughput SLO, because it is the critical path, not a footnote — instrument "records transitioning stale→fresh per build" and alert if it's zero across N builds (today it would be zero forever, because nothing repairs PNU). **(3)** The verifier must refuse to run against a 0-byte or schema-less DB (Round 2). **(4)** Add a second build run to CI so the active-flip/versioning path executes at least once against real data before anyone trusts it — today it has run exactly once in history. The 3 a.m. scenario I actually fear: someone reruns the build to "fix" the warnings, it picks the empty DB, writes 0 records, the verifier reports "Verified 0 active records … Clean: 0," exit 0 — and the dashboard goes green on an empty database.

### Mayo — the PNU backlog is a severity question, and "machine_verified" must mean a test was passed

Two forward-looking points. **First**, on the backlog: a record marked `stale` because its PNU `requires_repair` is making the *right* error-statistical move — withholding a claim that has not passed its check. Good. But there is no notion of *how severe* the PNU check was, so "fresh" (when it ever occurs) will mean only "PNU didn't flag itself," not "the belief-network context passed a test that would have caught it if wrong." Concrete fix: when PNU repair lands, record the PNU verifier's *error probability* or at least its check version + outcome in `belief_network_context`, so `fresh` carries a severity, not just a boolean. **Second**, the unreachable `machine_verified`: the verifier currently appends a `verification_events` row and walks away (`verify:641-664`); it never updates `review_status`. So the one state that *should* mean "this record passed a battery of tests" is never set. Either the state is meaningless and should be deleted (Smith's view), or — my preference — **the verifier should, on a clean pass, `UPDATE` the record's `review_status` to `machine_verified` inside the same transaction that writes the pass event.** That makes the category earn its meaning: `machine_verified` ⇔ "passed the §11 battery on `build_run_id` X." Minimum test: run builder → verifier on a clean fixture, assert the record's `review_status` flips to `machine_verified`; run on a dirty fixture, assert it stays `unreviewed`. Note the interaction with Wright: flipping `review_status` changes `payload_hash` (it's in the hashed set, `verify:380`), so this fix and the hash-envelope fix must land together.

### Gil — source-packet manifests prove intent, not consumption; provenance must record the activity

I gave the manifest-vs-consumption point under Bender's banner; the provenance-specific amendment is this. Stage 2's per-call record (spec §9) stores model name, prompt template hash, source packet manifest + hash, output hash, grounding result. That is a good *Entity* inventory and a partial *Activity* record, but it still has no *Agent* accountability beyond a model string and no `wasDerivedFrom` edge linking the generated field to the *specific source spans* it claims to summarize. Without span-level derivation edges, you cannot answer the only question that matters in a retraction: "this LLM sentence — which source did it come from, and is that source still valid?" Concrete fix: require every Stage 2 output field to carry a `wasDerivedFrom: [source_span_id, …]` list, and make the freshness invalidator (the overseer already has `invalidator.py`) mark the LLM field stale when any cited span's hash changes. That closes the loop between Stage 1's support sets and Stage 2's generated prose. Without it, Stage 2 provenance is a receipt for a transaction whose goods are unspecified.

### Haack — the plan still has no model of mutual support, and Stage 2 will paper over the gap with prose

My structural worry compounds in Stage 2. Today there is no representation of one claim securing another or of evidence's independent security (Round 2). Stage 2 proposes "competing-account summary" and "rebuttal synthesis" — generated *prose about* relations the data model does not represent. That inverts the dependency: prose should render structure, not substitute for it. Concrete amendment: **before any Stage 2 prose about support/rebuttal, add Stage 1 structural fields for inter-claim support edges and independent-security scores** (both deterministically derivable from the existing `supporting_papers`/`contradicting_papers`/argumentation edges you already load and currently discard for this purpose). Then the generated prose, if you must have it, is constrained to *describe* those edges and can be checked against them. The crossword has to have crossings before you can write a paragraph about how the answers fit.

### Smith — freeze the ontology and ground each category in an observable, or it will be renamed every six months

Forward-looking, the taxonomy churn (Round 2) will recur on every corpus expansion unless the categories are pinned to reality. When the corpus grows past indoor-environment psychology into, say, clinical trials or qualitative studies, `answer_shape ∈ {toulmin, field_map, comparison, mechanism, review_synthesis, mixed, unknown}` will sprout `procedure`, `case_series`, `contrast_pair` (the brief already had some of these and lost them), and `defeaters.target_kind` will need new members. Each rename breaks `payload_hash` (Wright) and every downstream switch statement. Concrete fix: **publish a versioned ontology file** (`contracts/ontology/aepl_vocabularies.v1.json`) with, per term, (a) a textual definition, (b) the *observable structural property* that makes a record an instance (not a label-prefix match), and (c) an `is_a`/`part_of` relation to a parent. New terms require a version bump and a migration note. This is the BFO discipline: every category names a kind with identity conditions, and the conditions are written down before the data is built, not reverse-engineered from whatever the upstream signal happened to spell.

### Goble — Phase 3's rendered verifier doesn't exist, and "who runs it" is unanswered

Spec §11's rendered-page verifier (`verify_article_epistemic_render_contract.py`) — the Selenium-style checks for mobile overflow, console errors, network errors, visible provenance badges — **does not exist as a file** (confirmed). AEPL-PHASE-3 cannot be evaluated because its acceptance instrument is unwritten. And the spec never says *who runs it or when*: in CI on every PR? on every deploy? against staging and production both (spec §13 implies production)? Concrete fixes: **(1)** write the render verifier as a headless-browser check that runs in CI against a built page fixture *and* as a post-deploy smoke against the live URL, with the same assertion set, so local and production cannot diverge silently. **(2)** Make it FAIR-reproducible: pin the browser version, ship the fixture page, document the command. **(3)** Gate Phase 4 on Phase 3's verifier being green on the 2 currently-renderable records *and* on a stale record's warning rendering — because the warning path is what 758 papers will actually show, and no one has looked at whether 758 warning banners are a usable page or a wall of yellow.
